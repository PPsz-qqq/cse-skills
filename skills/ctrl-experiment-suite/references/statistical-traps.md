# Statistical traps in this field

Ordered by how often each trap causes a rejection or a correction. Each entry names the trap, the
axes where it bites, the symptom a reviewer sees, and the repair. Read this before declaring
results frozen.

## T1 Single-seed delta

**Axes.** `det`, `track`, `reid`, and any learned `cnav` or `filt` component.

**Trap.** Two arms are compared with one training run each and the proposed arm wins by 0.8 mAP. The
0.8 is a seed difference, because the run-to-run spread of one configuration is routinely larger
than the difference being claimed.

**Symptom.** No run count, or `averaged over 3 runs` with no dispersion, or dispersion shown for
the baseline only.

**Repair.** At least 3 seeds per arm on the identical seed list, spread reported, comparison on the
mean. If one run exists, write `single seed` beside the number and treat it as a pilot. Never report
a single-seed delta as an improvement in any section.

## T2 Test-set tuning

**Axes.** all five.

**Trap.** Hyperparameters, thresholds, the checkpoint, or the architecture variant are chosen on
test-split performance, then the test split is reported as an unbiased estimate. Each selection step
raises the reported value above the population value, and the inflation grows with the number of
configurations tried.

**Symptom.** No validation split is mentioned. The paper reports exactly the configuration that
maximizes the metric with no selection story. A threshold figure peaks at the reported operating
point.

**Repair.** Carve a validation split before any tuning, tune only on it, evaluate the frozen
configuration on test once, and state how many configurations were tried. Where the split is
official with no validation portion, cross-validate over the training portion, or declare the tuning
explicitly and treat the reported number as optimistic. Never select on test and call it held out.

## T3 Cherry-picked throughput

**Axes.** `det`, `track`, `reid`, `cnav`.

**Trap.** The proposed method's FPS is measured on the newest accelerator, in half precision, at a
small resolution, with detection excluded from the timed region, with warm-up discarded, reporting
the best of several repeats. The baseline's FPS is copied from its paper on older hardware at a
different resolution with detection included. The pair is presented as an efficiency advantage.

**Symptom.** A throughput column with no device, no batch size, and no statement of what the timing
includes. Baseline FPS values inconsistent with the baseline's own reported hardware.

**Repair.** Time every arm on the same device, precision, resolution, batch size, and timed region,
and state all five. Report repeats and spread, not one timing and not the best timing. Where a
baseline cannot be re-timed, mark it `reported, different hardware, not comparable` and keep it out
of the efficiency argument.

## T4 Favorable noise covariance

**Axes.** `filt`, `cnav`.

**Trap.** The proposed estimator is given, or tunes its way to, `Q_k` and `R_k` matching the
simulator's true noise, while the baseline keeps conservative or mis-specified covariances. The
proposed filter wins on RMSE and its `ANEES` sits near the expected value, because the test data were
generated by the model that filter assumes.

**Symptom.** One arm's covariances are called `tuned` or `set to the true values` while the
baseline's are called `standard`. A consistency plot for the proposed filter only, and no
sensitivity analysis.

**Repair.** Give every arm the same noise information, or give none of them the true values and run
a mis-specification sweep as a separate experiment. Print the covariance settings per arm and report
consistency for every arm. When the proposed estimator adapts online, give the baseline equal
adaptation opportunity or declare the adaptation as the component under test.

## T5 Unpriced communication cost

**Axes.** `cnav`, and distributed `filt`.

**Trap.** A distributed method is compared against a baseline that exchanges less information, or
against a centralized solution, with no message accounting. Accuracy improves because more data
moved and the improvement is attributed to the algorithm.

**Symptom.** No bytes or message counts anywhere. A communication section reporting only latency. A
distributed claim whose update needs a global quantity, such as an average over all agents computed
at one node.

**Repair.** Report bytes per agent per step and messages per step for every arm, counted by one rule
including headers. Hold the budget fixed when comparing two methods, or report the
accuracy-against-cost frontier instead of a single point that falls on the favored side. State which
node holds which state, and label any arm needing global information as centralized and as a bound.

## T6 Metric convention drift

**Axes.** `det`, `track`, `reid`.

**Trap.** One metric name means different computations across the table. COCO-style against
VOC-style AP, `MOTA` from two evaluation tools, `mAP` with and without re-ranking, `AP_S` on
different area ranges, or a silently changed maximum-detection count.

**Symptom.** A row whose value is not plausible against the others, or a protocol section naming the
dataset but not the evaluator.

**Repair.** Write the metric convention into the protocol block, name the evaluation script and its
version, and evaluate every arm with one invocation of one evaluator. Mark a copied number from
another convention as `not comparable` and put it in a separate block of the table.

## T7 Selection among many configurations reported as one result

**Axes.** all five.

**Trap.** Twelve variants are tried, the best becomes the method, and the baseline was tuned less.
The reported value is a maximum over twelve draws and its margin partly reflects that selection.

**Symptom.** The method section describes exactly the winning combination with no mention of the
search. An ablation table where every component helps.

**Repair.** State the search space and how the configuration was chosen. Report the chosen
configuration's seed spread, not only its best seed. Where the search was wide, report the variant
count or their distribution so a reader can discount the value. Report components that consistently
failed.

## T8 The margin is below discrimination

**Axes.** `det`, `reid`, `track`.

**Trap.** Two arms differ by 0.1 mAP on a benchmark whose seed spread is 0.4. The difference is
written as an improvement because it is positive.

**Symptom.** Dispersion is in the table, larger than the reported delta, and the text still says
`outperforms`.

**Repair.** Apply the ladder in [statistics-and-seeds.md](statistics-and-seeds.md). If the interval
on the difference contains zero, write `the comparison is inconclusive at this run count`, not `no
difference` or `on par`, and say what the benchmark can and cannot resolve at this run count.
Equivalence needs a pre-declared margin and an equivalence test.

## T9 Simulation presented as a field result

**Axes.** `cnav`, `filt`, and remote-sensing `det`.

**Trap.** A simulator with idealized sensing produces a clean result and the abstract says the
method `achieves` a positioning accuracy without qualifying it as simulated. Robotics and remote
sensing reviewers read the unqualified sentence as a field or hardware claim.

**Symptom.** No platform, no sensor, no site. A `real-world` claim supported by a synthetic figure.
A sensor model with round-number parameters and no calibration reference.

**Repair.** Label every result with its evidence class, `simulation` or `field`, in the caption and
in the prose. For a field claim, describe the platform, the sensors, the site, the conditions, and
the failures. Where the simulation-to-field gap is unknown, say it is unknown and do not
extrapolate. A field-deployment claim requires field data.

## Trap audit

Run before any freeze. Answer each line with the axis, the artifact, and `pass`, `fail`, or `not
applicable`.

```text
[ ] T1  every compared arm has the same seed list and a stated run count
[ ] T2  the tuning split and the reported split differ, and the selection is described
[ ] T3  every throughput number names device, precision, resolution, batch size, timed region, repeats
[ ] T4  covariance settings are printed per arm and no arm sees information the others lack
[ ] T5  bytes per agent per step are reported for every distributed arm
[ ] T6  every metric names its evaluator and convention, and one evaluator handled all arms
[ ] T7  the configuration search space and selection rule are stated
[ ] T8  no delta smaller than the dispersion is written as an improvement
[ ] T9  simulation and field results are labeled in tables and in prose
[ ] T10 the comparison family and any correction are stated
[ ] T11 run counts are per arm and were fixed before running
[ ] T12 the aggregation rule is stated and per-unit spread is shown
[ ] T13 abstract, tables, captions, and conclusion reconcile on every shared number
[ ] T14 every baseline is labeled reported or re-implemented, with the published value shown
[ ] T15 no abstract number carries a not-comparable verdict
```
